# 0011. Contract resolution: dotted references, resolved in isolation at validate and publish time

- Status: Accepted
- Date: 2026-10-28

## Context

An agent's Brief names its input and output contracts with dotted references such as
`contracts.TaskList`. [ADR 0008](0008-contracts-and-configuration.md) validated these as names
only and left resolving them to execution. The registry changes that: each agent version stores
the JSON Schema of its contracts, so they can be diffed and used without Python, and a version's
content hash covers them. Its schemas have to be known when the agent is published, before it
ever runs, and a reference that names nothing should be caught by `conveyor validate`, not at
publish time or mid-run.

Contracts are ordinary Python modules in the factory project (`<root>/contracts.py`), next to
`agents/` and `factories/`. One process may validate or publish several projects, and those
projects can each have a module called `contracts` that defines different models under the
same names.

## Decision

- **References keep their current syntax.** Every part but the last names a module and the
  last names an attribute: `contracts.TaskList` is `TaskList` in `<root>/contracts.py` or
  `<root>/contracts/__init__.py`, and `contracts.review.Verdict` is `Verdict` in
  `<root>/contracts/review.py`. The attribute must be a Pydantic `BaseModel` subclass.
- **Resolve at validate and publish time** (`conveyor.contracts`). This amends ADR 0008's
  "resolving belongs to execution". `conveyor validate` reports a reference that does not
  resolve as an issue on the `brief.input` or `brief.output` line, with the reason: the module
  is missing, the attribute is missing or not a model, the model has no JSON Schema, or
  importing raised (its exception type and message are included). Only agents inside a
  project (in `<root>/agents/<name>/`) are resolved; a standalone agent folder has no root to
  resolve against and keeps the name-only check.
- **Only the project root is searched for the top-level module.** It must exist as a file or
  package in the root, so a reference cannot silently resolve to an installed package of the
  same name; names of the standard library, Conveyor and Pydantic are reserved.
- **Imports are isolated per call.** Resolving holds a lock and, for its duration, sets aside
  any module already imported under the reference's top-level name, puts the root first on
  `sys.path`, drops cached path finders for the root and turns off bytecode writing so nothing
  is written into the project. Afterwards it removes every module imported from the root, which
  covers the contract package and the sibling modules it imports, restores `sys.path` and the
  set-aside modules, and drops the root's cached finders again. Packages merely stored under the root, such as a
  virtual environment inside the project, are not treated as project modules. The returned
  class stays usable afterwards; it is fully built (`model_rebuild`) before the module is
  dropped, because forward references can only resolve while it is importable.
- **Schemas are JSON Schema 2020-12 in validation mode**, generated by Pydantic with `$schema`
  set, nested models under `$defs`, and returned as a fresh copy of plain JSON data. Pydantic's
  output is deterministic for a given model, so the same contract always gives an equal schema.

## Alternatives considered

- **Keep references as strings until execution** (ADR 0008 as written) — the registry could not
  store or diff contract schemas, and a broken reference would surface only when a run reached
  that stage.
- **Entry-point syntax, `package.module:Attr`** — unambiguous about where the module ends, but
  the dotted form is already in every `agent.yaml`, matches the scorer references in factory
  files, and the module/attribute split is not ambiguous when the last part is always the
  attribute.
- **Schema files committed next to `agent.yaml`** — no code runs at validate time, but the
  Pydantic model and its file would drift unless regenerated, and execution needs the model
  anyway for typed output. One source of truth wins.
- **Import in a subprocess per project** — stronger isolation (nothing touches the parent's
  modules), but it costs an interpreter start per validation and the model class cannot cross
  the process boundary, while the in-process approach returns the class for later use.
- **`importlib.util.spec_from_file_location` under a mangled module name** — avoids touching
  `sys.path`, but a contract module's imports of its own siblings (`from contract_helpers
  import ...`) would not resolve, and model `__module__` names would be mangled in schemas and
  error messages.

## Consequences

- **Validating or publishing a project now runs its contract modules.** They are project code
  and are trusted like any code in the repository being worked on: validate only projects you
  would run. The README's validate section says so. Execution (M3) will import them anyway.
- A contract module whose import has side effects, or that calls `sys.exit()`, is reported as
  an issue rather than ending the process, but its side effects still happen.
- The isolation is process-wide state guarded by a lock, so resolving is serialised; this is
  fast enough for validation and publishing. Modules a contract imports from outside the
  project (Pydantic, the standard library, installed packages) stay imported, as they would in
  any Python process.
- A sibling module in the project whose name is already imported from elsewhere resolves to
  that other module. Keeping shared helpers inside the contract package avoids this.
