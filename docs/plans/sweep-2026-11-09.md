Status: **F-01 to F-04 and F-14 have fixes in review** (see [Fixes](#fixes)). F-05 to F-13 are

## Summary

- The baseline is green and stable: `make check` passes, 448 tests, 99.82% branch coverage, no
  flaky test in four differently seeded runs. The 29 Postgres tests also pass (run against a
  local Postgres 16, not the Docker image).
- **No critical or high findings.** No data loss, no wrong version IDs, no broken sequence
  numbers, no corrupted store in any probe, including 48 concurrent publishes from 12 processes.
- Five medium findings. Three are performance problems that grow with project size
  (F-01, F-02, F-03), one is a crash on hostile YAML (F-04) and one is the Postgres migration
  gap ADR 0012 already records, now reproduced, including a deadlock between threads (F-05).
- Nine low findings: mostly places where the code is slightly weaker than an ADR or a comment
  says.
- My recommendation: fix F-01 to F-04 before M3. F-05 matters as soon as M3 opens a store from
  more than one thread or process on Postgres. The rest can wait.

### F-01 Contract modules are imported once per reference per agent (medium, confirmed)

**Measurement.** Synthetic projects from the benchmark script, all agents naming
`contracts.TaskList` and `contracts.CodeChanges` from the reference factory's `contracts.py`:

| Command | Wall time | Peak memory |
|---|---|---|
| `conveyor validate` on 100 agents | 3.68 s | 91 MB |
| `conveyor validate` on 1,000 agents | 31.92 s | 99 MB |
| Parse and validate the same 1,000 `agent.yaml` files without contracts | 1.19 s | |

A cProfile run of `validate_path` on the 1,000-agent project shows 2,000 calls to
`resolve_contract`, 2,001 module executions and 20,000 Pydantic model class builds: 60 of 66
profiled seconds.

**Reproduction of the count.** A `contracts.py` that increments a counter file when imported,
and one agent with `input: contracts.A` and `output: contracts.B`: after
`inspect_agent_folder`, the counter reads `2`.

**Cause.** `src/conveyor/model/checks.py:133-138` calls `resolve_contract_schemas(root, [ref])`
once per reference, and `src/conveyor/contracts/resolver.py:103` isolates each call, dropping
the module afterwards. Nothing is shared between agents: `_Validator` in
`src/conveyor/model/validate.py:45` caches agent folders, not contracts.

**Docs contradicted.** The docstring at `checks.py:124` says "its module is imported once" and
the comment at `src/conveyor/registry/service.py:248` says "each contract module is imported
once per publish". Both are true only when input and output are the same reference. Import side
effects (ADR 0011: "its side effects still happen") happen twice per agent.

**Proposed fix.** Resolve all of an agent's references in one isolated import, and let
`validate_path` share resolved schemas across the agents of one project for one run. Expected:
about 3 s for 1,000 agents (a 90% cut), and one import per publish. Generating the schema
inside the isolation also fixes F-14.

### F-02 Line diffs are quadratic and run inside `publish` (medium, confirmed)

**Measurement.** `conveyor.registry.diff.text_diff` on texts of unique lines with every tenth
line changed:

| Lines | Time |
|---|---|
| 2,000 | 0.04 s |
| 20,000 | 4.73 s |
| 100,000 | 179.21 s |

Ten times the lines costs about 118 times the time. `publish` builds this diff before it
returns (`service.py:502-508`), so publishing a regenerated 100,000-line eval dataset blocks for
minutes. `agent diff` has the same cost.

**A related accuracy problem.** In a file of 200 or more lines made mostly of repeated lines,
one changed line is reported as many: 300 identical lines with one changed gives `+150 −150`,
while the same edit in 150 lines gives `+1 −1`. The diff is still valid, but the counts in the
publish summary are wrong. Realistic YAML suites (repeated structure, unique values) were
correct in every case tried.

**Cause.** `src/conveyor/registry/diff.py:230` uses `difflib.unified_diff`, which is
`SequenceMatcher` with `autojunk=True`. Its matching is quadratic when changes are scattered,
and `autojunk` discards lines that make up more than 1% of a file of 200 or more lines.

**Proposed fix.** Strip the common prefix and suffix before matching (exact, linear, and enough
for the usual small edit in a large file), turn `autojunk` off, and above a line limit for the
remaining region report it as replaced rather than matching it. Expected: linear time; the
100,000-line case in well under a second. Diff text changes only for the two cases above.

### F-03 Commands that never touch the registry import SQLAlchemy and Alembic (medium, confirmed)

**Measurement.** Median of 7 runs, `.venv/bin/conveyor`:

| Command | Wall time |
|---|---|
| `python -c pass` | 19 ms |
| `conveyor --help` | 827 ms |
| `conveyor --version` | 751 ms |
| `conveyor validate examples/prd-to-pr` | 890 ms |
| `conveyor agent history implementer` | 745 ms |

Import cost, median of 9 runs of `python -c "import ..."`:

| Import | Wall time |
|---|---|
| `typer` | 84 ms |
| `conveyor.model` and `typer` (all that `validate` and `--help` need) | 229 ms |
| `conveyor.storage` | 611 ms |
| `conveyor.cli` | 723 ms |

**Cause.** `src/conveyor/cli.py:26-50` imports `conveyor.registry` and `conveyor.storage` at
module level. `conveyor.registry.service` imports storage, which imports SQLAlchemy (about
290 ms), both the SQLite and Postgres dialects, and Alembic (about 130 ms more).

**Proposed fix.** Import the registry and storage inside the `agent` commands. Expected:
`--help` and `--version` about 300 ms, `validate` about 400 ms (55 to 65% faster). The
six-process concurrency tests, the two slowest in the suite, pay this import per process too.
`conveyor/__init__.py` also spends about 50 ms in `importlib.metadata.version`; I would leave
that alone.

### F-04 Deeply nested YAML crashes with a traceback (medium, confirmed)

**Reproduction.**

```bash
python3 -c "print('x: ' + '['*500 + ']'*500)" > agents/implementer/agent.yaml
conveyor validate .
```

Ends with a Python traceback and `RecursionError: maximum recursion depth exceeded`. Depth 300
is reported normally; depth 500 crashes. The exit code is `1`, the same as "problems found",
only because that is what an uncaught exception gives. `agent publish` and `agent diff
--working` read the same file the same way.

**Cause.** ruamel's pure-Python composer recurses per nesting level
(`src/conveyor/model/loader.py:304`), and so does `_Converter.convert` (`loader.py:196`).
Neither is guarded. The loader already caps alias expansion "to keep a hostile or mistaken file
from hanging validation" (`loader.py:37-42`); nesting is the same class of input.

**Proposed fix.** Catch `RecursionError` in `parse_yaml` and report one positioned-at-start
issue, "nested too deeply". A test with depth 3,000.

### F-05 Concurrent first open of a Postgres store fails or deadlocks (medium, confirmed)

ADR 0012 records that migrations are not guarded on Postgres. This is the reproduction.

**Processes.** Eight processes calling `Store.open_url` on an empty database at the same
instant, six rounds: 40 opens succeed and 8 fail with `DatabaseUnavailableError: ... duplicate
key value violates unique constraint "pg_type_typname_nsp_index"`. The same test on SQLite: 48
of 48 succeed.

**Threads.** Eight threads in one process doing the same never finish. `pg_stat_activity` shows
one session `idle in transaction` after `CREATE TABLE alembic_version` and the others waiting on
its transaction; the Python stacks show three threads waiting for a psycopg connection lock.
Alembic's `context` is one object per process, so one thread's `env.py` runs on another
thread's connection. On SQLite, `BEGIN IMMEDIATE` is taken before Alembic starts, which is why
80 of 80 threaded opens succeed there.

**Cause.** `src/conveyor/storage/store.py:59-60` and `src/conveyor/storage/migrate.py:48-68`:
nothing serialises `command.upgrade` on Postgres.

**Proposed fix.** Take `pg_advisory_xact_lock` on the migrating connection before
`command.upgrade`, and hold a module-level `threading.Lock` around Alembic. No migration script
changes. ADR 0012 names this gap in its Consequences, so closing it wants a short new ADR or
a note in the next one rather than an edit.

**Why it matters for M3.** DBOS, the API server and the CLI will open the same store from more
than one thread and process. On SQLite today that is safe.

### F-06 `agent list` runs one query per agent (low, confirmed)

**Measurement.** Registry with 200 agents (one of them with 1,000 versions): `list_agents` runs
402 statements (201 `BEGIN`/`SELECT` pairs) in 105 ms in process. `conveyor agent list` takes
0.97 s against 0.75 s for an empty registry, so about 0.2 s, growing by about 0.5 ms per agent.

**Cause.** `src/conveyor/registry/service.py:400-402` calls `registry.latest(name)` for each
name from `registry.agents()`.

**Proposed fix.** One repository method returning the latest version of every agent in a single
query. Expected: 2 statements and about 5 ms whatever the count.

### F-07 `publish` serialises the whole snapshot seven times (low, confirmed)

**Measurement.** One agent with a single 50 MB eval file:

| Command | Wall time | Peak memory |
|---|---|---|
| `agent publish` (first version) | 2.50 s | 259 MB |
| `agent publish` (unchanged) | 4.37 s | 358 MB |
| `agent publish` (one-line prompt edit) | 4.98 s | 361 MB |
| `agent show` | 2.73 s | 307 MB |
| `agent diff --working` | 3.44 s | 307 MB |

A profile of the unchanged publish shows `canonical_json` called 7 times on the full snapshot,
0.61 s each: 4.28 s of the run. A suite of 1,000 small files (4 MB) is unaffected: 0.81 s and
87 MB.

**Cause.** The snapshot's validator serialises it to check it has a canonical form
(`src/conveyor/registry/snapshot.py:165`); `content_id` serialises it again (`:192`);
`publish` serialises it again to store it (`service.py:481`); loading the previous version
serialises that one three more times (`canonical.py:69`, `snapshot.py:165`, `:233`) and once
more for its content ID (`service.py:280`).

**Proposed fix.** Serialise once per snapshot and reuse the bytes for the check, the ID and the
store; on load, trust the bytes just verified. Expected: 7 passes down to 2 or 3, roughly half
the time and memory. This only matters for suites of many megabytes.

### F-08 A read-only command writes when a `-wal` file was left behind (low, confirmed)

**Reproduction.** Publish a second version from a process that exits without closing the
store (`os._exit` in place of `Store.close`), leaving `conveyor.db-wal` and `-shm`. Then:

```text
before:  conveyor.db 7cc0e781a50d   conveyor.db-wal 70d5196a9a0c (12,392 bytes)
$ conveyor agent history implementer      (prints v2 and v1 correctly)
after:   conveyor.db 16471bd33d53   (-wal and -shm removed)
```

The database file's content and modification time change. On a clean store the three read
commands leave every file byte-identical, as ADR 0015 says.

**Cause.** `src/conveyor/storage/database.py:88-89` opens a writable folder's database
normally with `PRAGMA query_only=ON`. `query_only` refuses SQL writes but not the checkpoint
SQLite runs when the last connection closes. ADR 0015 says "writes are refused by SQLite, not by
convention" and that read commands "leave a project exactly as they found it".

**Proposed fix.** Set `SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE` on read-only connections (Python
3.12+, `Connection.setconfig`), so a leftover `-wal` is read and left in place. No data is at
risk either way, which is why this is low.

### F-09 `sys.exit()` in a contract module's `__getattr__` ends the process (low, confirmed)

**Reproduction.** `contracts.py` containing `def __getattr__(name): sys.exit(3)`;
`resolve_contract(root, "contracts.X")` raises `SystemExit: 3` instead of
`ContractResolutionError`.

**Cause.** `src/conveyor/contracts/resolver.py:128` catches `(Exception, SystemExit)` around
the import, but `_model` (`:139`) and `model_rebuild` (`:113`) catch only `Exception`. ADR 0011
says a module that calls `sys.exit()` "is reported as an issue rather than ending the process".

**Proposed fix.** Catch `SystemExit` in those two places as well, with a test for each.

### F-10 Diff rendering splits lines on separators other than `\n` (low, confirmed)

**Reproduction.** Instructions whose second line holds U+2028 and a form feed;
`conveyor agent diff NAME --working` prints that one added line as three, two of them without
a `+`:

```text
        +line two with
        separator and
         formfeed
```

The third looks like a context line. The `+N −M` counts are right.

**Cause.** `src/conveyor/registry/diff.py:679` uses `str.splitlines()`, which also splits on
`\r`, `\v`, `\f`, `\x1c` to `\x1e`, `\x85`, U+2028 and U+2029. The diff itself is built from
`\n` only (`diff.py:210`).

**Proposed fix.** Split on `"\n"`. One-line change and a test.

### F-11 Control characters in a publish message reach the terminal (low, confirmed)

**Reproduction.** `conveyor agent publish NAME -m $'fix\x1b[31m RED \x07bell'` is accepted;
`conveyor agent history NAME | cat -v` shows `^G` in the output (Click strips the colour
sequence only when output is not a terminal).

**Cause.** `src/conveyor/registry/service.py:472-473`: the author must be one printable line
"because a control character could rewrite the terminal it is printed to" (`:433-435`), but the
message is only checked for being non-blank.

**Proposed fix.** Either refuse control characters other than newline and tab in messages, or
escape them when printing. Refusing changes what the public CLI accepts, so this needs a
decision.

### F-12 An eval suite of `.` is accepted (low, confirmed)

**Reproduction.** Set `quality_gate.suite: "."`. `conveyor validate` reports no problems, and
`agent diff --working --summary` shows `eval case added (agent.yaml)` and
`eval case added (prompt.md)`: the agent's own definition files are snapshotted as eval cases.

**Cause.** `_check_relative_path` (`src/conveyor/model/types.py:108-116`) accepts `.`, and
`checks.py:110` only checks that the suite exists.

**Proposed fix.** Reject a suite that is the agent folder itself. This is a new validation rule
on `agent.yaml`, so it is a configuration format change.

### F-13 Non-string mapping keys are reported unclearly (low, confirmed)

**Reproduction.** Add the line `true: 1` at the top of an `agent.yaml`:

```text
agents/implementer/agent.yaml:1:7: [1]: keys should be strings
```

The key is at column 1, the path `[1]` reads as a list index, and the key written was `true`.

**Cause.** `src/conveyor/model/loader.py:234-246` accepts `bool` and `int` keys (`bool` is an
`int`), so Pydantic reports them later, at the value's position.

**Proposed fix.** Report non-string keys in the loader, at the key, quoting what was written.

### F-14 Contract schemas are generated outside the import isolation (low, confirmed)

**Reproduction.** A model whose `json_schema_extra` hook does `import lazy_helper` (a sibling
module in the project): `cannot resolve contract 'contracts.M': no JSON Schema can be generated
for it: ModuleNotFoundError: No module named 'lazy_helper'`.

**Cause.** `src/conveyor/contracts/schema.py:131-136` calls `contract_schema(model)` after
`resolve_contract` has left the isolation and removed the project's modules and path.

**Proposed fix.** Generate the schema inside the isolation. Naturally part of F-01.

## Checked and found clean

- **Loader.** Empty file, non-UTF-8, NUL and other forbidden characters (correct line and
  column), a byte order mark, duplicate keys, tags, merge keys, recursive aliases, the alias cap,
  integer values for float fields (`temperature: 0`), block mappings 300 deep, Windows-style and
  parent-relative paths. Parsing and validation are linear in file size.
- **Contracts.** No module or `sys.path` entry leaks after resolving, including sibling modules;
  no bytecode is written into the project; edits between two calls are seen; same-named modules
  in two projects stay separate across threads; recursive and forward references resolve; every
  non-model target (a value, a plain class, a Pydantic dataclass, a generic alias, `BaseModel`
  itself, a missing name) is reported clearly. Schemas with `set` and `frozenset` defaults are
  identical across six hash seeds, so IDs do not depend on `PYTHONHASHSEED`.
- **Storage.** A garbage, truncated or zero-byte database, a corrupt or missing object,
  `.conveyor` or `objects` being a file, and a schema from a newer Conveyor each give a one-line
  message and exit code 1, never a traceback. A corrupt or missing snapshot is repaired by
  publishing the same content again, as ADR 0012 says. 12 processes publishing 6 different edits
  into one fresh store, 4 rounds, with readers alongside: every publish succeeded, sequences are
  contiguous, no consecutive duplicate content, no temporary files left. Threads opening one
  SQLite store are safe. Queries use the unique indexes; no index is missing. The migration
  check costs 2 ms per open.
- **Registry.** The README's example IDs (`893e1fa01106`, `7b514a755dad`) reproduce exactly.
  An unchanged publish leaves every file in `.conveyor/` with the same size and modification
  time. `.gitkeep`-only suites, hidden files, symlinks and special files behave as ADR 0013
  says. Sequence refs, short and malformed prefixes and out-of-range numbers are handled.
- **CLI.** Every command's exit code matches the README for: no registry, unknown agent, unknown
  version, malformed ref, malformed name, a folder that is not a project, an invalid working
  copy, and `diff --exit-code` with and without differences.
- **Cross-cutting.** No naive datetimes, no swallowed exceptions beyond the one documented
  `RegistryNotFoundError` in `list_agents`, and no unclosed connections or files (the suite runs
  with warnings as errors, and read commands leave no `-wal` or `-shm` on a clean store).

## Could not check

- **Windows and macOS.** Path handling, `os.replace` under contention, case-insensitive file
  systems and Unicode-normalised names were read, not run. CI has a Windows job.
- **Non-root permissions.** Everything ran as root, so read-only folders and unreadable files
  were not exercised, and the one test that needs them was skipped (S-3).
- **The Docker path for Postgres.** The Docker daemon is not running here. The Postgres tests
  ran against a local Postgres 16 instead of the `postgres:17-alpine` container CI uses.
- **Durability across power loss.** The fsync calls were read, not tested.
- **`live` tests.** None exist yet.
- **The UI.** Out of scope; only `make ui-check` was run.

## Notes for M3

- **Snapshots are stored whole for every version** (ADR 0013 chose this when snapshots were
  kilobytes). Two versions of an agent with a 50 MB eval suite, differing by one prompt line,
  take 97 MB, and nothing collects unreferenced objects. Run artifacts will be far larger than
  snapshots; decide on per-file objects or a collector before they share this store.
- **Alembic is not thread-safe** (F-05). Open the store once per process and share it, or fix
  F-05 first.
- **Resolving contracts runs project code under a process-wide lock.** A server that validates
  on request will serialise on it, and today pays one import per reference (F-01).
- **Read-only opens fail after a migration is added** until something writes (ADR 0015). M3's
  first new migration makes this visible to anyone running `agent list` after upgrading.

## How this was measured

A benchmark script kept outside the repository (not committed) generated synthetic projects by
copying the reference factory's `contracts.py` and writing N agent folders, and timed each
command as a child process, reading peak memory from `getrusage`. Commands used:

```bash
python -X importtime -c "import conveyor.cli"
conveyor validate <project with 100 or 1,000 agents>
conveyor agent publish|show|history|list|diff ... --project <project>
uv run pytest -q --no-cov -p randomly --randomly-seed=<seed> --durations=12
CONVEYOR_TEST_POSTGRES_URL=postgresql+psycopg://... uv run pytest -m postgres --no-cov
```

Profiles used `cProfile` on `validate_path` and `publish` only, where a number looked wrong.
